# 屏幕延迟的真正原因：DWM 合成帧率卡死

## 一句话结论

系统处处要等，**不是 CPU / 内存 / 磁盘忙**，而是 **DWM（桌面窗口管理器）的合成帧率被卡死在 21.4 FPS**。

屏幕设置里明明写着 1920x1080 @ 120Hz，实际只有 21.4 帧/秒上屏，于是每次键盘输入、右键、鼠标悬浮最多要等 **47ms** 才显示出来。

**修复方式：重新下发一次显示模式（或 Win+Ctrl+Shift+B 重置显卡驱动）。**

---

## 二、现象

- 键盘输入、右键点击软件、鼠标悬浮，都要很久才「显现」
- 打开任务管理器一看，CPU 只占 10% 左右，什么都不忙
- 容易误判成「CPU 的问题」或「CPU 缓存爆了」

> CPU 缓存没有「爆」这种故障模式。L3 缓存未命中只会让**某个程序**变慢，不会让整机画面卡。真要是缓存抖动，会看到某个核心长期跑满 100%。

---

## 三、排查顺序（可复用方法论）

核心思路：**自下而上逐层量数据，每层都要有实测数字，不要靠感觉猜。**

| 层 | 检查项 | 健康值 | 本次实测 |
|---|---|---|---|
| CPU 算力 | 总占用 / 处理器队列长度 | <70% / <2 | 12% / 1.5 ✅ |
| 内核中断 | DPC 时间 / 中断时间 | <5% | 0.26% / 0.27% ✅ |
| 降频 | 频率百分比 / 性能上限 | 有睿频、上限 100% | 166% / 100% ✅ |
| 磁盘 | 磁盘队列长度 | <2 | 0.07 ✅ |
| 内存 | Pages/sec（换页） | <100 | 2.83 ✅ |
| 文件 I/O | 小文件写+读+删 | <5ms | 0.44ms ✅ |
| 注册表 | 打开+读 | <1ms | 0.016ms ✅ |
| 屏幕读取 | 桌面 BitBlt 256x256 | <10ms | **46.6ms ❌** |
| **显示合成** | **DwmFlush 周期** | **= 刷新周期** | **46.9ms ❌ → 8.32ms ✅** |

前七层全部正常，第八层开始崩，问题就锁定在**显示合成链路**上。

---

## 四、关键武器：DwmFlush

判断屏幕延迟的黄金指标不是 CPU，而是 **`DwmFlush()`**——它等待下一次 DWM 合成，耗时直接等于合成周期。

```powershell
Add-Type -TypeDefinition @'
using System; using System.Diagnostics; using System.Runtime.InteropServices;
public class Vsync {
  [DllImport("dwmapi.dll")] static extern int DwmFlush();
  public static string Rate(int sec){
    var sw=Stopwatch.StartNew(); long c=0;
    while(sw.Elapsed.TotalSeconds<sec){ DwmFlush(); c++; }
    return string.Format("实际合成帧率 = {0:F1} FPS", c/(double)sec);
  }
  public static string Flush(int n){
    double t=0,max=0;
    for(int i=0;i<n;i++){ long a=Stopwatch.GetTimestamp(); DwmFlush();
      double ms=(Stopwatch.GetTimestamp()-a)*1000.0/Stopwatch.Frequency; t+=ms; if(ms>max)max=ms; }
    return string.Format("DwmFlush x{0}: 平均={1:F2}ms 最大={2:F2}ms => {3:F1} FPS", n, t/n, max, 1000.0/(t/n));
  }
}
'@
[Vsync]::Flush(200)
[Vsync]::Rate(5)
```

正常值：120Hz 屏 ≈ **8.3ms**，60Hz 屏 ≈ **16.7ms**。

### 本次实测

| 状态 | DwmFlush | 实际帧率 |
|---|---|---|
| 修复前 | 46.9 ms | **21.4 FPS** ❌ |
| 切到 60Hz | 16.60 ms | 60.2 FPS ✅ |
| 切回 120Hz | **8.31 ms** | **120.3 FPS** ✅ |
| 修复后复核（200次） | 8.32 ms（最大 9.41） | **120.2 FPS** ✅ |

还要做一步**排除「空闲降频」**的对照：让画面持续刷新（不断 InvalidateRect + UpdateWindow）再测。

- 空闲时：46.91ms
- 有画面刷新时：46.57ms

两边一样 → 说明是**真卡死**，不是省电策略。

## 五、辅助定位：屏幕读取耗时

`GetDC(NULL)` + `BitBlt` 抓屏要经过合成后的桌面，能反映显示链路延迟。

- 纯内存 BitBlt 基线：**0.013ms**（说明 GDI 本身没问题）
- 屏幕 BitBlt 256x256：**46.6ms** ❌（健康值 <10ms）
- 修复后同一测试：**8.46ms** ✅

两者对比就能把「GDI 慢」和「显示合成慢」区分开。

---

## 六、根因

显示驱动 / eDP 链路的状态机卡死：GPU 报告 120Hz 模式，但呈现路径锁在一个固定 46.9ms 的节拍上出不来。CPU、GPU 占用都极低（GPU 仅 2%），所以从任务管理器完全看不出来。

**本机高嫌疑对象：**

| 对象                                             | 版本                               | 说明                   |
| ---------------------------------------------- | -------------------------------- | -------------------- |
| NVIDIA 驱动                                      | 32.0.16.1062（Dell OEM，2026/6/11） | 呈现路径的直接责任人           |
| `OrayIddDriver Device`                         | 17.50.19.949                     | 向日葵**虚拟显示驱动**，挂在显示栈上 |
| `OrayUSBVHCI` / `Oray Virtual Game Controller` | 1.0.0.0                          | 向日葵的 USB / 手柄驱动，常驻加载 |

注意：SunloginService 服务是**停止**的，但驱动本身仍然加载着。虚拟显示驱动干扰主显示路径是这类故障的经典原因。

## 七、修复与复发自救

### 应急（按快慢排序）

1. **Win + Ctrl + Shift + B** —— 重置显卡驱动，1 秒，最快
2. 设置 → 显示 → 刷新率，120 和 60 来回切一次
3. 重新应用一次分辨率

### 程序化重新下发显示模式

```powershell
Add-Type -TypeDefinition @'
using System; using System.Runtime.InteropServices;
public class FixMode {
  const uint DM_BITSPERPEL=0x40000, DM_PELSWIDTH=0x80000, DM_PELSHEIGHT=0x100000, DM_DISPLAYFREQUENCY=0x400000;
  [StructLayout(LayoutKind.Sequential, CharSet=CharSet.Ansi)] public struct DEVMODE {
    [MarshalAs(UnmanagedType.ByValTStr,SizeConst=32)] public string dmDeviceName;
    public ushort dmSpecVersion, dmDriverVersion, dmSize, dmDriverExtra; public uint dmFields;
    public int dmPositionX, dmPositionY; public uint dmDisplayOrientation, dmDisplayFixedOutput;
    public short dmColor, dmDuplex, dmYResolution, dmTTOption, dmCollate;
    [MarshalAs(UnmanagedType.ByValTStr,SizeConst=32)] public string dmFormName;
    public ushort dmLogPixels; public uint dmBitsPerPel, dmPelsWidth, dmPelsHeight, dmDisplayFlags, dmDisplayFrequency;
    public uint dmICMMethod, dmICMIntent, dmMediaType, dmDitherType, dmReserved1, dmReserved2, dmPanningWidth, dmPanningHeight; }
  [DllImport("user32.dll", CharSet=CharSet.Ansi)] public static extern bool EnumDisplaySettings(string d, int m, ref DEVMODE dm);
  [DllImport("user32.dll", CharSet=CharSet.Ansi)] public static extern int ChangeDisplaySettingsEx(string d, ref DEVMODE dm, IntPtr h, uint f, IntPtr p);
  public static string Reapply(int hz) {
    var dm = new DEVMODE(); dm.dmSize=(ushort)Marshal.SizeOf(typeof(DEVMODE));
    EnumDisplaySettings(null, -1, ref dm);
    dm.dmFields = DM_PELSWIDTH|DM_PELSHEIGHT|DM_BITSPERPEL|DM_DISPLAYFREQUENCY;
    dm.dmPelsWidth=1920; dm.dmPelsHeight=1080; dm.dmBitsPerPel=32; dm.dmDisplayFrequency=(uint)hz;
    return "ChangeDisplaySettingsEx -> " + ChangeDisplaySettingsEx(null, ref dm, IntPtr.Zero, 0, IntPtr.Zero);
  }
}
'@
[FixMode]::Reapply(60)    # 先切 60
Start-Sleep 4
[FixMode]::Reapply(120)   # 再切回 120，把卡死的流水线冲开
```

### 长期

- 用 **DDU** 干净卸载后装最新 NVIDIA 驱动（别用 Dell OEM 版）
- 不用向日葵就卸掉它的虚拟显示驱动

## 八、顺手发现的隐患（非本次原因）

用 `fltmc filters` 和 `Win32_SystemDriver` 能列出所有第三方内核驱动，本机挂了不少：

- **360 全家桶 8 个驱动**：`360AntiAttack` / `360AntiHijack` / `360AntiSteal` / `360Box64` / `360Camera` / `360FsFlt` / `360netmon` / `360Sensor`
  - 其中 `360AntiSteal`(402120) / `360Box64`(382310) / `360FsFlt`(382300) 三个微过滤驱动同时挂在 4 个卷上，每次文件 I/O 都要过一遍
  - 事件日志里 `luafv`（Windows UAC 文件虚拟化驱动）被反复拦截：`This driver has been blocked from loading`
- **3 份「鲁大师硬件防护」驱动**：`lockerx_protect` / `LudashiProtect64` / `MaxProtectProtect`，签名都是「成都鲁易科技有限公司」
- `tcc-g15`（Dell 风扇控制）会直接读写 EC，可能引发 SMU/SMI 停顿
- VBS 已开启（`VirtualizationBasedSecurityStatus=2`），HVCI 关闭

本次这些都没造成延迟（文件 I/O 实测 0.44ms），但都是隐患。

## 九、本次用到的命令速查

```powershell
# 看 Top CPU 进程
Get-Process | Sort-Object CPU -Descending | Select-Object -First 20 Id,ProcessName,CPU

# DPC / 中断 / 队列（抓峰值，不是看平均）
Get-Counter '\Processor(_Total)\% DPC Time','\Processor(_Total)\% Interrupt Time','\System\Processor Queue Length' -SampleInterval 1 -MaxSamples 60

# 每核占用（i5-12500H：0-7 是 P 核，8-15 是 E 核）
Get-Counter '\Processor(*)\% Processor Time' -SampleInterval 1 -MaxSamples 20

# 是否降频
Get-Counter '\Processor Information(_Total)\% of Maximum Frequency','\Processor Information(_Total)\% Performance Limit'

# 文件系统微过滤驱动栈（第三方挂钩全在这）
fltmc filters

# 正在运行的非微软内核驱动
Get-CimInstance Win32_SystemDriver | Where-Object {$_.State -eq 'Running'}

# 显示驱动版本与日期
Get-CimInstance Win32_PnPSignedDriver | Where-Object {$_.DeviceClass -eq 'DISPLAY'} | Select-Object DeviceName,DriverVersion,DriverDate,DriverProviderName

# 活动显示拓扑（真实刷新率）
# 用 QueryDisplayConfig，或简单看：
Get-CimInstance Win32_VideoController | Select-Object Name,CurrentHorizontalResolution,CurrentVerticalResolution,CurrentRefreshRate

# Windows 自带能耗诊断（15个错误/9个警告，主要报电源策略）
powercfg /energy /duration 60 /output energy.html

# 谁在请求高精度定时器
powercfg /requests
```

## 十、经验总结

1. **「系统不忙但很慢」优先怀疑显示合成，不是 CPU。** 任务管理器的 CPU 数字对显示链路故障完全无感。
2. **`DwmFlush()` 是判断屏幕延迟最快的一招**，一次测量就能定性。
3. **一定要做「空闲 vs 有画面刷新」的对照**，否则会把省电降频误判成故障。
4. **重新下发显示模式是万能第一招**，成本极低，能冲开大多数显示驱动状态机卡死。
5. 用 `fltmc filters` 看清有多少第三方驱动在文件 I/O 路径上，是很实用的体检手段。
